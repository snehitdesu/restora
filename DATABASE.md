# RESTORA (working name Aharos) — Database

_Current as of 2026-10-09: 117 models; 27 SQLite migrations and 17 PostgreSQL migrations (the PostgreSQL history starts from a baseline of the first SQLite migrations). Compatibility details and the PostgreSQL write-ups: `docs/postgres.md`; production roles, pool, isolation, load, backup / DR: `docs/production-infrastructure.md`; RLS design: `docs/postgres-rls.md`._

## Two engines, one schema

| | SQLite | PostgreSQL 16 |
|---|---|---|
| Used for | development, the default test suite, the desktop app | **production**, the PostgreSQL test suite, the PostgreSQL browser E2E |
| Schema | `prisma/schema.prisma` | generated by `node scripts/pg-schema.mjs` into `prisma/postgres/schema.prisma` (git-ignored): provider switched, explicit `DECIMAL(p,s)` precision applied |
| Migrations | `prisma/migrations` (27) | `prisma/postgres/migrations` (17, **committed**: the only replayable path to a production database; baseline `20261004130000_baseline`) |
| Apply | `prisma migrate deploy` (desktop: its own migrator, which also runs trigger bodies) | `DATABASE_URL=postgresql://… npm run db:pg:deploy` — never `db push`, never `migrate reset` on a real database |

Rules for changing the schema: edit `prisma/schema.prisma`; classify every new `Decimal` in `DECIMAL_FIELDS` (`scripts/pg-schema.mjs`; generation fails otherwise); write both migrations (SQLite ones are plain `ADD COLUMN` / `CREATE` where possible, because a table rebuild silently drops triggers); bump `EXPECTED_MIGRATION` in `src/server/ops/readiness.ts`; CI checks both histories against the schema for drift (shadow database for PostgreSQL) and against a freshly deployed database.

Money and quantities are `Decimal`. Enumerations are `String` plus a centralized value list validated by Zod at the boundary (`src/constants/enums.ts`): portable across both engines and free of destructive enum migrations.

## Tenancy

```
Organization ─ Outlet ─ Department / Table / Printer / …
```
Every business row carries `organizationId` (and `outletId` where operational), indexed. The application enforces isolation on every query (`orgScope`, `outletScope`, `authorizedOutletIds`, `assertOutletInOrg`) and is tested with cross-organization and cross-outlet negatives in every domain suite. PostgreSQL row-level security is **designed, not applied** (`docs/postgres-rls.md`): safe only with per-transaction tenant settings that need a real deployment to verify, and unnecessary while one organization owns the database. Multi-outlet inside one organization is supported; multi-restaurant tenancy is intentionally deferred.

## History the database refuses to rewrite

`AuditLog` and `InventoryLedger` are append-only **in the database**: `BEFORE UPDATE` and `BEFORE DELETE` triggers on both tables abort with "… is append-only" (SQLite `RAISE(ABORT)`; PostgreSQL function `restora_refuse_change()` plus statement triggers that also refuse `TRUNCATE`). The triggers apply to every connection — the application role, the schema owner, a hand-typed query — and survive backup and restore (drilled). Created by migration `20261021100000_append_only_rate_limit`; the readiness check lists any that are missing (a later SQLite table rebuild would drop them). Only `withAppendOnlyGuardsOff` (`src/server/db/appendOnly.ts`) lifts them, for wiping a **disposable** database (demo seed, Coders' Cafe reset, test fixtures); nothing in the running application calls it. Corrections are new rows (`InventoryLedger.correctionOfId`, opposite entries), never edits. Other history is protected by convention and `onDelete: Restrict`: `Payment`, `Refund`, `LoyaltyTransaction`, `PettyCashTxn`, frozen snapshots (`StockCountLine.bookQty`, `OrderItem.unitCost`, invoices).

On PostgreSQL the production role setup (`scripts/ops/pg-roles.sql`: `restora_owner` / `restora_app` DML-only / `restora_backup`) additionally revokes `UPDATE, DELETE, TRUNCATE` on those tables from the application role.

## Inventory is derived, never typed

Stock is the signed sum of `InventoryLedger.qty`:
```
OPENING_BALANCE + PURCHASE_RECEIPT + TRANSFER_IN + PRODUCTION_OUTPUT
  − SALE_CONSUMPTION − ISSUE (department → department, same cost) − TRANSFER_OUT − WASTAGE − PRODUCTION_CONSUMPTION
  ± COUNT_ADJUSTMENT / OTHER_ADJUSTMENT = on-hand
```
Weighted-average cost is per outlet (`OutletMaterialCost`). Expiry is reported per received batch (earliest-expiry-first derivation); stock is not held per batch (audit IN-14).

## Idempotency and uniqueness (the second line behind the services)

| Guarantee | Constraint |
|---|---|
| One consumption per business event | `InventoryLedger.sourceRef` unique |
| A retried order is the same order | `Order (organizationId, idempotencyKey)` unique + `requestHash`; `Order (outletId, source, externalRef)` unique |
| A replayed webhook is a no-op | `WebhookEvent (provider, eventId)` unique |
| No duplicate gateway capture / refund | `Payment (provider, providerRef)`, `Refund (organizationId, providerRef)` unique; client-key uniqueness on refunds, vendor payments, GRNs, bills, rounds |
| No double booking | `ReservationSlot (tableId, slot)` unique |
| One run of a daily job | `JobRun (name, scopeKey, runDate)` unique |
| One checklist task per item per day | `Task (templateItemId, runDate)` unique |
| One loyalty award per order and type | `LoyaltyTransaction (customerId, orderId, type)` unique |
| Gap-free invoice numbers | per-outlet, per-financial-year counter row, issued inside the settlement transaction |

## Transactions

Service transactions are SERIALIZABLE with a bounded retry; new-order placement runs at READ COMMITTED (measured and documented, `docs/production-infrastructure.md` §6-§7). Contention beyond the retries returns `503 Busy` + `Retry-After`. Settlement is serialized per outlet and edits per order in-process (`keyedLock`), so a hot row queues instead of aborting. The shared rate-limit store (`RateLimitWindow`, `RATE_LIMIT_STORE=database`) is one atomic upsert per limited request and falls back to per-process counting if the database errors.

## Verification

| Check | Where |
|---|---|
| Both migration histories apply to an empty database and have no drift | CI jobs "SQLite" and "PostgreSQL 16" |
| The whole Vitest suite on both engines (including `tests/db/*`: append-only, concurrency, Decimal precision, invariants, conflict classification) | CI |
| Integrity of a live database (migrations finished, constraints validated, no overpaid / uncovered / refunded-beyond-payment orders, no orphan audit or ledger rows, optional per-table fingerprint) | `node scripts/ops/db-verify.mjs --url …` |
| Backup → destroy → restore → fingerprint compare, with tampered-backup and wrong-key refusals | `scripts/ops/backup-drill.mjs` (re-run on the current schema 2026-10-09: 10/10) |
| Point-in-time recovery | `scripts/ops/pitr-drill.mjs` (2026-10-05; not repeated since) |

`prisma/seed.ts` rebuilds demo data through the real services and wipes a **disposable** database first; it must never be pointed at a real one.
